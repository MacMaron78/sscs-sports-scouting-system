# Design and Development of a Web-Based Sports Scouting and Coordination System for Sports Agencies and Athletes

> Working structure for the final academic report. Replace bracketed prompts with verified project details and actual findings. Remove instructions before submission. Never report planned activities as completed or invent participants, results, approvals, or deployment evidence.

## Preliminary pages

- Title page and team details, using the institution's required format
- Declaration and supervisor approval, if required
- Dedication and acknowledgements, if required
- Abstract: problem, objective, methods, system, actual evaluation, key results, and conclusion
- Table of contents
- List of figures, tables, and abbreviations

## Chapter One: Introduction

### 1.1 Background
Summarize the sports scouting context and cite verified sources.

### 1.2 Problem statement
State the specific athlete exposure and talent-discovery problem addressed.

### 1.3 Project goal and objectives
Use the approved proposal wording; explain any approved changes.

### 1.4 Scope and delimitations
Describe users, Uganda-focused context, web application scope, exclusions, and limitations.

### 1.5 Significance and report organization
Describe intended beneficiaries without claiming benefits not established by evaluation.

## Chapter Two: Literature Review

Present the reviewed literature, relevant systems, conceptual/theoretical grounding, synthesis, research gap, and how the gap informed the design. Verify every source and citation. Do not rely on unsupported claims or references that cannot be located.

## Chapter Three: Methodology

### 3.1 Research and system-development design
Explain the Design Science Research activities and any mixed-methods approach actually followed.

### 3.2 Population, sample, and sampling
Report the intended population and actual participant counts, groups, recruitment method, inclusion criteria, and deviations from the proposal.

### 3.3 Data collection
Describe only interviews, questionnaires, document analysis, and usability evaluation that actually occurred. Include approved instruments in appendices.

### 3.4 Data analysis
Explain the actual thematic coding and descriptive statistical methods used.

### 3.5 Ethics and data protection
State the approval body/reference and date only if approval was obtained. Describe consent, privacy safeguards, restricted storage, retention, and any deviations. Do not imply approval if it was not granted.

### 3.6 System design and implementation method
Describe the actual architecture, React frontend, Node/Express API, PostgreSQL data model, development iterations, and any changes from planned Figma or Agile work.

## Chapter Four: System Analysis, Design, and Implementation

Include:

- Functional and non-functional requirements with traceability to evidence.
- Use cases/user journeys and role/access rules.
- Architecture diagram and deployment topology.
- ER diagram, data dictionary, and relevant schema decisions.
- Interface designs or screenshots; identify whether they are actual implementation screens or earlier prototypes.
- API and module descriptions.
- Security, validation, and privacy controls.
- Implemented features and known limitations.

## Chapter Five: Testing, Evaluation, and Results

### 5.1 Functional testing
Provide test IDs, setup, expected and actual outcomes, pass/fail, date, and environment. Distinguish mocked API tests from database-backed or end-to-end tests.

### 5.2 Demonstration and usability sessions
Report actual participant counts and groups, task completion, observed issues, and participant feedback. Include SUS response count, individual or appropriately anonymized summary scores, mean and range, and explain the scoring method.

### 5.3 Expert review
Summarize each expert's anonymized findings and recommendations.

### 5.4 Changes resulting from evaluation
Link each important finding to a decision, code/documentation change, and retest result.

### 5.5 Results and limitations
Present actual evidence. State small sample, demonstration environment, self-reported data, and other limitations. Do not generalize beyond the study.

## Chapter Six: Discussion, Conclusion, and Recommendations

Relate the actual findings to each project objective and research question. State which objectives were met, partially met, or not met, with evidence. Discuss limitations, recommendations, and possible future work. Keep excluded features (native mobile apps, video hosting, AI recommendations, talent prediction, advanced analytics, live match analysis) as future work unless the approved scope changed.

## References

Use the institution's required citation style. Verify author, title, year, publication, and DOI/URL for every reference.

## Appendices

- Approved participant information and consent materials
- Final interview guide and questionnaire
- Document-analysis records (de-identified)
- Usability task sheets and SUS records (appropriately anonymized)
- Expert-review summaries
- Test cases/results
- Additional diagrams and screenshots
- Deployment/demo details, if available

## Final evidence checklist

- [ ] Every objective is answered with evidence.
- [ ] Actual sample and evaluation results are reported accurately.
- [ ] Ethics approval and consent are described truthfully.
- [ ] Tests identify mocks versus a real database or browser.
- [ ] Evaluation findings are linked to changes and retests.
- [ ] Demo URL and deployment date are included only if the demo was deployed.
- [ ] Screenshots contain no real passwords, private messages, or unnecessary personal data.
- [ ] Citations and appendices follow institutional requirements.
